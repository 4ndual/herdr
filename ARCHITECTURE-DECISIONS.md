# Architecture decisions

This file records fork-only core changes for the update pipeline and FIXER AGENT. Before resolving an upstream merge or an end-to-end failure, preserve the goals and public seams below. Apply the update-pipeline matrix: prefer upstream-shaped seams and the smallest fork surface; rearchitect the custom side when either side breaks; deprecate a custom feature when native functionality fully replaces its goal.

## ADR-001: Persistent invisible tabs

**Goals.** Hide a tab from tab-bar geometry, hit testing, and ordinary navigation without closing its panes, PTYs, layouts, agents, notifications, or runtime registrations; keep the state across restart; provide a mouse-visible `Make invisible` tab-menu item; expose stable-ID `tab.list {hidden}` and `tab.show` APIs so `invisible-dash` can list and restore tabs. Never allow the last visible tab to be hidden, and move focus to a visible neighbor when hiding the active tab.

**Alternatives considered.** Closing/archiving the tab (destructive and semantically different); removing it from `Workspace.tabs` (loses ownership and pane identity); a plugin-only record (cannot preserve host runtime state); a vector-index API (unstable across reorder/restore); a generic visibility toggle without explicit list/show methods.

**Decision and why.** Keep the tab in `Workspace.tabs` and add `Tab.hidden` plus serde-default `TabSnapshot.hidden`; filter only visible tab UI/navigation while retaining all runtime ownership. Use the existing public stable tab ID (`workspace public ID:tab number`) in API payloads, `tab.list` with optional `hidden`, and `tab.show {tab_id, focus?}`. Keep `Make invisible` host-owned in both TUI and API-backed dispatch paths because it mutates core state; keep restore in the plugin. The seams to preserve are snapshot capture/restore, active-tab visibility invariant, tab geometry/hit testing, and API schema/bridge capability checks. If upstream adds native tab hiding, migrate to its state and APIs rather than retaining parallel fork fields; if upstream changes tab identity, adapt the plugin contract at the stable-ID seam.

## ADR-002: `open_plugin_panes` and `OpenPluginPane`

**Goals.** Let a WASM UI plugin open a visible, interactive PTY pane for long-running work, with the correct plugin root, declared entrypoint, placement, and live stdout/stderr, so autonomous update steps and their fixer agent are visible. Gate the effect by an explicit manifest capability and preserve legacy action invocation for direct/API callers and older hosts.

**Alternatives considered.** Continue using `InvokePluginAction` (background detached thread and captured log, no visible PTY); hard-code version-dash panes in the host; add a capability query/fallback ABI; make the plugin draw fake progress instead of running the real command in a PTY.

**Decision and why.** Add `OpenPluginPane {entrypoint, placement}` to the fork guest ABI, `open_plugin_panes` to manifest capabilities, and host routing through the existing plugin-pane placement implementation (overlay/split/zoom/tab). Version-dash declares focused tab entrypoints and emits this effect after the same model safety gates; its old actions remain declared. Capability filtering is intentional: an old host may drop the effect rather than guess a fallback, while direct action compatibility remains. Preserve the ABI enum/serialization, capability filter, pane placement seam, entrypoint resolution, and plugin-root execution environment. If upstream gains an equivalent native pane-opening API, rebase the guest onto that API and remove the fork effect/capability; do not fork host placement further.

## ADR-003: In-process WASM UI plugin bridge

**Goals.** Provide fork-only in-process WASM UI modules for right-panel, bottom-dash, tab-surface, pane-overlay, context-menu, and pane-graphics/text surfaces; deliver host state/input; allow narrowly declared API reads/writes, plugin actions, toasts, file input, pane movement/graphics, collectors, and pane opening; support hot reload and live-handoff registry/state preservation. This backs both invisible-tab restoration and version-dash panes while remaining compatible with upstream's out-of-process plugin v1.

**Alternatives considered.** Use upstream plugin v1 only (out-of-process manifest commands, no in-process frame rendering); hard-code each dashboard into the host; let WASM access the socket/filesystem without capability declarations; use a separate host implementation for every surface; make visibility/update behavior external scripts with no host bridge.

**Decision and why.** Keep the generic `UiPluginManager`/manifest bridge, vendored `herdr-ui-plugin-api`, declared surfaces and capabilities, host-side effect filtering, `ui_input_file` state envelope, collector boundary, and plugin registry/hot-reload/handoff seams. Plugins own presentation and workflow-specific commands; the host owns tab/runtime invariants, placement, and capability enforcement. `api_read` permits `tab.list {hidden:true}` and `api_write` permits `tab.show`; `plugin_actions` and `open_plugin_panes` remain explicit rather than implicit. Preserve upstream's out-of-process v1 path instead of replacing it. If upstream supplies native in-process modules with equivalent capability isolation, rearchitect plugins to that contract and deprecate duplicate bridge code; if upstream only changes v1, adapt the bridge at manifest/registry seams rather than embedding plugin-specific logic in core.

## ADR-004: Version-dash update pipeline

**Goals.** Make “update latest” an observable, gated test-then-promote pipeline: open a visible pane for each autonomous step, stream command output, atomically publish `pipeline.json` and a per-stage log, show working/terminal state and elapsed time, require a passing receipt whose SHA matches the test binary before promotion, and never promote with failing E2E. On any merge conflict or E2E failure, invoke the FIXER AGENT in the same visible pane with logs plus this file as context.

**Alternatives considered.** Existing detached `InvokePluginAction` with in-memory 64-KiB logs; silent background shell scripts; build directly into the watched/plugin target; promote without a receipt/hash gate; automatic restart or live handoff; a tracker inferred from archived files rather than atomically written state.

**Decision and why.** Keep update scripts as the authoritative build/promotion gates, run them through manifest tab-pane entrypoints and `OpenPluginPane`, and atomically replace state in `HERDR_PLUGIN_STATE_DIR/pipeline.json` while teeing a stage log. Keep test build and HR promotion distinct: build/sanity-check the test binary, require its matching `verify-test.json`, then atomically stage/copy promotion; restart remains opt-in. Preserve `pipeline.json` field semantics consumed by the version-dash collector/model, explicit repository and instance paths, receipt/hash validation, and no-promotion-on-failure behavior. The host pipeline/fixer must run the agent CLI inside the pane, not as an invisible subprocess. If upstream provides a native visible task runner/tracker with equivalent receipts and failure handoff, adopt it and deprecate the scripts/collector pieces; otherwise rearchitect only the custom side around upstream APIs to minimize merge conflicts.

## ADR-007: Upstream 0.8.0 input rearchitecture under the plugin key broadcast

**Goals.** Land upstream's 0.8.0 input model — per-source input identity (`InputSourceId`, `LOCAL_INPUT_SOURCE`), `TerminalInputContext` replacing the ad-hoc `popup_pane.is_some() || mode == Terminal` test, lease-based key repeat (`input_leases`) replacing `suppressed_repeat_keys`, and `clear_input_source`/`release_input_source_headless` — while keeping ADR-003's delivery of key presses to WASM UI modules that declared `keyboard_input`.

**Alternatives considered.** Keep the fork's `suppressed_repeat_keys` path and skip upstream's lease system (permanently forks the hottest input path and loses multi-client correctness); drop `offer_key_to_ui_plugins` and let plugins go back to never receiving keys (silently revokes a negotiated capability, and doctor-dash's safety argument depends on the broadcast existing); make the offer a *consume* so plugins can claim keys while adapting to the lease model (an ABI change smuggled in under a merge, which would invalidate the "keys are broadcast but not consumable" guarantee plugins were written against).

**Decision and why.** Adopt upstream's shape wholesale in `route_client_events_from` and re-attach the fork hook as a single leading `self.offer_key_to_ui_plugins(key.as_key_event())` before `terminal_input_context()` is sampled. This is matrix rule 3 (custom functionality breaking new upstream code → rearchitect the custom side) plus rule 4 for repeat suppression: upstream's leases fully replace `suppressed_repeat_keys`, so the fork field is deprecated rather than carried. Offer-before-dispatch preserves the exact pre-merge fork ordering, so plugin-visible behaviour is unchanged and the offer stays a non-consuming broadcast. Both sides' additions at the same insertion points (`TerminalInputContext`/`InputSourceId` vs the restart-sentinel helpers, `clear_input_source` vs the plugin-effect drain, and both test blocks) were kept — they were additive, not competing. The seams to preserve are: the offer is not a consume, it runs before context sampling, and `source_id` threads through every terminal key path.

## ADR-008: Render signalling and tick ownership after 0.8.0

**Goals.** Keep fork-owned repaint triggers (dashboard/plugin input, resume-picker overlay transitions) working after upstream replaced the `render_dirty` `AtomicBool` with a `RenderSignal` that distinguishes generic requests from PTY-origin requests, and keep the fork's `next_dash_tick` collector/plugin tick while upstream deletes its own animation timer.

**Alternatives considered.** Re-add an `AtomicBool` beside `RenderSignal` (two sources of truth for "is a frame pending", and the headless server's PTY-discard optimisation would silently ignore fork repaints); classify fork repaints as `request_pty(pane_id)` (wrong origin — a dashboard repaint has no originating pane and would be discarded when no client is showing that pane); keep `next_animation_tick`/`sync_headless_animation_timer` alive as fork state (they had no remaining callers on either side and would be dead fork surface forever).

**Decision and why.** Route every fork repaint through `render_dirty.request_generic()`, matching upstream's own idiom in `app/popup.rs` and `app/theme_sync.rs`. Generic is the correct classification: these repaints have no originating PTY, so the headless server must not treat them as PTY-only updates it may drop. Delete `next_animation_tick` and `sync_headless_animation_timer` (matrix rule 4 — upstream removed the feature and every caller), but retain `next_dash_tick`, which is live fork state driving `usage_host`/`goal_host`/`historial_host`/`harness_host`, plugin collectors, manifest hot-reload, and per-frame plugin dispatch in both the direct and headless loops. In the headless render decision, combine both sides rather than choosing: `foreground_changed || theme_changed || (interaction && !render_neutral_mouse_motion) || plugin_action_changed`. Upstream's parenthesised term suppresses frames for render-neutral mouse motion; the fork's `plugin_action_changed` must stay a peer disjunct so a plugin action still forces a frame even when the triggering input was motion.

## ADR-009: Rebasing fork hosts onto upstream's plugin-v1 and appearance seams

**Goals.** Keep the fork's collector, harness, resume-picker, agent-spawn and tab-creation paths working against 0.8.0's changed host APIs without forking those APIs: upstream's out-of-process plugin v1 spawn helper, the new `host_terminal_appearance` parameter, and the terminals-aware workspace display name.

**Alternatives considered.** Keep a fork-local copy of the old `command_for_argv` (duplicates process-spawn policy — Windows batch resolution, relative-program handling — and would drift from upstream's plugin v1); pass `None` for `host_terminal_appearance` at fork call sites (fork-spawned panes would silently theme differently from upstream-spawned ones); keep calling `Workspace::display_name()` by making the fork re-export the now-`#[cfg(test)]` method (re-exposes an API upstream deliberately narrowed).

**Decision and why.** Adopt upstream's API at each seam. `plugin_collector::run_collector` now calls `command_for_argv_in_dir(program, args, plugin_root)` and drops its own `current_dir` call — the helper sets the cwd and resolves a relative `./collector` program against it, which is exactly the plugin-root execution environment ADR-002/ADR-003 require, so this *reduces* fork surface. Every fork call site of `new_argv_command_with_extra_env`, `split_pane_argv_command`, `create_tab_argv_command` and `spawn_argv_command` threads `self.state.host_terminal_appearance` immediately after `host_terminal_theme`, mirroring upstream's own call sites so fork-spawned panes inherit identical theming. `AppState::build_pane_close_record` uses `display_name_from_terminals(&self.terminals)`, which stays a pure read because `AppState` already owns `terminals`. This is matrix rule 2 throughout: upstream changed under custom functionality, so the custom side moved.

## ADR-010: Conflict policy for generated and additive files

**Goals.** Resolve `Cargo.lock`, `Cargo.toml` and the documentation conflicts in the way that minimises future merge conflicts, per matrix rule 1.

**Alternatives considered.** Hand-merge `Cargo.lock`'s five conflict hunks (a generated file; a hand-merge is unverifiable and re-conflicts on every future dependency change); keep the fork's `version`, `license` and `repository` metadata in `Cargo.toml` (permanent three-line conflict on every upstream release); rewrite the upstream documentation section instead of appending to it.

**Decision and why.** For `Cargo.lock`, take upstream's file wholesale and regenerate against the merged manifest with `cargo metadata`, which re-derives the fork's path crates (`goal-dash-core`, `herdr-ui-plugin-api`, `version-dash-model`, …) and `wasmtime` deterministically. A regenerated lock is reproducible and conflict-free next time; a hand-merged one is neither. For `Cargo.toml`, take upstream's file — including the 0.8.0 version bump, the Apache-2.0 relicense, the `repository` change, and the new `ctrlc`/`jsonc-parser`/`wmi`/Win32 dependencies — and re-apply only the fork's additive blocks (path dependencies, the `host-images` feature gate, `[dev-dependencies] wat`, and `[workspace]`). For `configuration.mdx`, keep upstream's prose intact and append the fork's `toggle_goal_panel` and `[ui]` `usage_strip`/`goal_panel` sections. In all three the rule is the same: upstream owns the file's shape, the fork owns clearly delimited additions.

## ADR-011: Completing the ADR-001 tab-visibility surface

**Goals.** Make the tab-visibility feature described in ADR-001 actually compile and be reachable, and give upstream's newly relocated construction sites a defined value for the fork's fields.

**Alternatives considered.** Give `TabInfo.hidden` a `#[serde(default)]` and drop it from struct literals (serde defaults do not apply to Rust struct construction, so this does not compile and would also hide the field from API consumers); have the CLI's `tab list` filter to visible tabs only (a second, divergent default beside the `tab.list` API contract); leave `tab.show` out of `WRITE_METHODS` (ADR-003 explicitly requires `api_write` to permit it, and `invisible-dash` cannot restore a tab without it).

**Decision and why.** Three defects predating this merge blocked the build and are repaired here rather than worked around: `"tab.show"` had been appended *after* the final brace of `ui_plugin_api_bridge.rs` instead of into `WRITE_METHODS` (a syntax error); `TabListParams { workspace_id }` in `cli/tab.rs` omitted the fork's `hidden` field; and `FocusInput` construction in `plugin_focus.rs` omitted `pane_id`. `tab.show` now sits with the other `tab.*` writes — it can only make an already-owned tab visible again, strictly less destructive than `tab.close`, which is already in that row, so it needs no separate capability. The CLI passes `hidden: None`, the same "no visibility filter" default as the `tab.list` API, keeping the CLI a thin wrapper rather than a second contract. `TabInfo.hidden` is populated from `tab.hidden` at upstream's relocated construction site in `app/creation.rs`: per ADR-001 a hidden tab retains full runtime ownership, so it still gets a `TabInfo` and visibility is *reported* there, with filtering left to `tab.list`. `FocusInput.pane_id` is resolved with the same `public_pane_number` + `public_pane_id_for_number` pair `app::ids::public_pane_id` uses, so a focus payload joins against `pane.list` without a second lookup.

## ADR-012: Foreground steal hysteresis vs upstream's promote-on-background-input

**Goals.** Keep the fork's foreground-assignment policy (a non-foreground client's typing only steals the shared-pane size after the holder has been quiet for `FOREGROUND_STEAL_HYSTERESIS`, so two people typing at once do not thrash shared-pane resizes and clip each other's rows) while satisfying upstream's new 0.8.0 contract that background mouse motion promotes the moving client once and is render-neutral thereafter.

**Alternatives considered.** Delete `foreground_policy` and take upstream's promote-on-any-input (reintroduces the documented resize-thrash and row-clipping bug the module exists to fix, and upstream ships no equivalent, so matrix rule 4 does not apply); edit upstream's `background_mouse_motion_promotes_once_then_becomes_render_neutral` test to expect no promotion (hacking upstream to protect a fork behaviour, which rule 2 forbids); back-date the attach seed of `ClientConnection.last_active_at` by the hysteresis window so a never-typed holder is immediately stealable (tried and rejected — it makes *any* background input promote, which breaks the fork's own `fork_input_bare_keypress_does_not_promote_but_focus_gained_does` contract); thread a `has_real_input` flag through `ClientConnection`, `ClientActivity` and both activity constructors (same over-broad outcome, plus fork fields in three shared files).

**Decision and why.** The two contracts are not actually in conflict once the *event kind* is taken seriously: the fork's rule is about **typing** (`bare keypress must not promote`), upstream's new rule is about **pointer input** (`background mouse motion promotes once`). So promotion is now event-aware. A new fork helper `events_include_pointer_input` joins `events_include_focus_gained` in the immediate-promote branch, while keys, text and paste continue through `note_active_input`'s 2s hysteresis unchanged. A mouse event is an unambiguous "I am using this client" signal — the same class as an explicit window focus-gained, which the fork already promotes on immediately — and it is not the keystroke-thrash case the hysteresis was written for. This satisfies upstream's test without editing it, keeps the fork's anti-thrash contract and its own test green, and confines the change to one helper plus one branch condition. Matrix rule 3, resolved by narrowing the custom rule to the case it was actually written for rather than weakening it.

## ADR-013: Adapting upstream tests to documented fork surface

**Goals.** Let upstream's 0.8.0 test suite run green against fork surface that legitimately changes what those tests observe, without weakening either side's contract.

**Alternatives considered.** Delete the fork features the tests trip over (the `Make invisible` tab-menu row is required by ADR-001 and the usage strip by ADR-003, so this is not available); delete or `#[ignore]` the upstream tests (throws away upstream's real coverage and hides future regressions); hard-code new row indices and rect heights (re-breaks on the next change from either side).

**Decision and why.** Three upstream tests observe fork-modified surface and are adapted, not disabled. (1) `ui::tests::desktop_tab_bar_position_controls_geometry_and_mode_bar_placement` and `ui::tests::bottom_tab_bar_still_hides_when_single_tab` now set `app.usage_strip_enabled = false`, the convention the fork already uses for every other geometry test — these tests are about tab-bar placement, so removing the strip from the measurement keeps upstream's expected rects *literally unchanged* and lets future upstream geometry edits merge cleanly. (2) `app::input::modal::tests::tab_context_menu_lists_fork_between_rename_and_close` gains `Make invisible` in its expected list; upstream's actual contract there is the ordering assertion (`Rename < Fork < Close`), which still holds. (3) `app::input::mouse::tests::clicking_tab_context_menu_close_leaves_context_menu_mode` now resolves the `Close` row index from the live menu instead of hard-coding row 5, so it survives either side adding a row. Separately, `docs/next/api/herdr-api.schema.json` was regenerated through the project's own `HERDR_UPDATE_API_SCHEMA=1` path; it had never been regenerated after ADR-001, so the published schema now finally carries `TabInfo.hidden`, `TabListParams.hidden`, `TabVisibilityParams` and the `tab.show` method.

**Order-dependence made deterministic.** `workspace::tests::generated_workspace_ids_are_short_base32_handles` exists identically on both sides and asserted `id.len() <= 3` against `NEXT_WORKSPACE_ID`, a process-global counter. The merged suite builds more than 32² workspaces in one test binary, so the handle grows a character and the assertion fails on suite size rather than on any defect. The assertion now checks the property the test name claims — a `w` + base32 handle, short for any realistic workspace count — against `PUBLIC_ID_ALPHABET` and `encode_public_number` rather than the shared counter. Resetting the counter in the test was rejected: it is shared by every parallel test and a reset would hand out duplicate workspace ids elsewhere.

**Known non-defect.** `server::headless::tests` occasionally fails with `bind test listener: AddrInUse` under parallelism; whichever test binds first loses the race, so the reported test name changes between runs. It passes in a serial run and is not merge-induced — recorded here so a future fixer does not chase it as merge damage.

## ADR-014: Persistent invisible workspaces

**Goals.** Hide a workspace from the sidebar, its hit testing, and ordinary workspace navigation without closing its tabs, panes, PTYs, layouts, agents, notifications, or runtime registrations; keep the state across restart; provide a mouse-visible `Hide` workspace-menu item; expose stable-ID `workspace.list {hidden}`, `workspace.hide` and `workspace.show` APIs plus `herdr workspace hide/show` so a hidden workspace is always recoverable. Never allow the last visible workspace to be hidden, and move both focus and selection to a visible neighbour when hiding the active one.

**Alternatives considered.** A plugin-only `Hide` row appended through the ADR-003 context-menu bridge (a plugin can add the row but owns no core state, so there is nothing for it to call — a dead menu entry); closing or archiving the workspace (destructive and semantically different); removing it from `AppState.workspaces` (loses pane identity, public pane/tab numbering and worktree grouping); hiding every tab instead (`Workspace::set_tab_hidden` refuses the last visible tab by design, so this can never empty a workspace); reusing `collapsed_space_keys` (that is worktree-group presentation state keyed by repo, not a per-workspace property, and it is deliberately not persisted); shipping `workspace.hide` without `workspace.show` and leaving restore to a future dash, as ADR-001 did for tabs (tabs have `invisible-dash`; workspaces have no equivalent, so hiding would be unrecoverable).

**Decision and why.** Keep the workspace in `AppState.workspaces` and add `Workspace.hidden` plus serde-default `WorkspaceSnapshot.hidden`, mirroring ADR-001's `Tab.hidden`/`TabSnapshot.hidden` field for field. Filter in exactly one place: `ui::sidebar::workspace_list_entries_inner`. That function is the single funnel for which workspaces get a row — `compute_workspace_list_areas` derives sidebar geometry and hit testing from it, and `AppState::visible_workspace_order` derives `next_workspace`/`previous_workspace` from it — so one filter covers presentation, hit testing and navigation without a second visibility rule. This is a smaller surface than ADR-001 needed for tabs, which had tab-bar geometry, hit testing and `next_visible_tab` as three separate seams.

The mutator is `AppState::set_workspace_hidden`, not a `Workspace` method: the last-visible refusal and the focus/selection move are facts about the workspace *list*, which `Workspace` cannot see. It is the sole writer of the field, so the refusal and the neighbour move are enforced in one place for the TUI row, the API and the CLI alike, exactly as `Workspace::set_tab_hidden` is for tabs.

The API uses the existing public stable workspace ID. `workspace.list` takes an optional `hidden` filter with the same "no visibility filter" default as `tab.list` (ADR-011), so `{}` keeps deserializing and existing callers are unchanged; `WorkspaceInfo.hidden` *reports* visibility at every construction site because a hidden workspace retains full runtime ownership and still gets a `WorkspaceInfo`. `workspace.show` joins `workspace.create`/`focus`/`rename` in `WRITE_METHODS` for the same reason `tab.show` did — it can only make an already-owned workspace visible again, strictly less destructive than `workspace.close`. `workspace.hide` sits beside it.

The reveal path ships in the same change rather than being deferred. `herdr workspace list --hidden|--visible`, `herdr workspace hide <id>` and `herdr workspace show <id> [--focus]` mirror the `herdr tab` trio ADR-011 landed, and here they are load-bearing rather than convenience: tabs also have `invisible-dash`, workspaces have no dash equivalent, so the CLI is the only way back and cannot be left for later. The CLI stays a thin wrapper: `hidden` defaults to `None`, the same "no visibility filter" contract as the API, so it never becomes a second default.

User-facing documentation is the `docs/next/CHANGELOG.md` entry and the regenerated `docs/next/api/herdr-api.schema.json`, deliberately not the website reference pages. `socket-api.mdx` and `cli-reference.mdx` list neither `tab.show`/`tab.hide` nor `herdr tab hide`/`show` — those upstream-shaped, translated files carry no fork-only rows today, and adding some would create translation-parity work and a permanent conflict hunk on every upstream docs change for no reader that the changelog and the generated schema do not already serve. This is matrix rule 1 (upstream owns the file's shape), recorded here as a decision rather than left to look like an oversight.

**Two dispatch tables, not one.** A context-menu row must be added to BOTH `apply_context_menu_action` and `apply_context_menu_action_via_api`. A real sidebar click reaches the *second* one; the `_ =>` arm there forwards plugin actions and otherwise just calls `leave_modal`, so a row present only in the first table renders in the menu, closes cleanly when clicked, and does nothing at all. That is exactly how this feature shipped broken once — the menu-items assertions and the handler unit tests all passed because none of them clicked. The regression test `clicking_workspace_context_menu_hide_routes_through_api_path` drives `handle_mouse`, the way the sidebar does, and is the test that pins this.

The seams to preserve are snapshot capture/restore of `hidden`, the last-visible-workspace invariant, both context-menu dispatch tables, the single `workspace_list_entries_inner` filter that `visible_workspace_order` and the card areas both read, and the API schema/bridge capability rows. If upstream adds native workspace hiding, migrate to its state and APIs rather than retaining parallel fork fields (matrix rule 4); if upstream changes workspace identity, adapt at the stable-ID seam.
